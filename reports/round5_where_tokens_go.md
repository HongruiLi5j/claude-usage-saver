### 1. 通读/复核/网页调研类子 agent 改派给 Codex（skill 规则 + 习惯）
- **做什么**：在 model-router skill 里加规则。"通读一个目录写文档""交叉复核""查官方文档"默认用 `codex exec` 跑，结果写到文件。Claude 只读结论（≤1 页），关键结论抽查 1–2 处。
- **估计节省**：启用后这三类占 32.9%（9.33M/天）× 70–90% = 23–30% → **约 45–60M/周**。如果按普通日这类工作只有一半算，**约 20–30M/周（10–15%）**。
- **风险**：Codex 读错没人发现；要另外开 Codex 会话、看日志；有些复核本来就是为了给 Claude 的工作找第二意见，那正好适合 Codex。
- **难度**：中（写规则 + 一个调用 Codex 并只回摘要的小脚本）。
- **怎么验证**：weekly_compare 的"子 agent·Opus/Sonnet 每天成本"和子 agent 数，同时对比同类任务的派发次数。抽 3 个 Codex 报告和代码对照，记录错误率。

### 2. 无人值守/多会话通宵运行：把上下文上限压到 150k，空闲会话先压缩或退出（设置 + 运行规范）
- **做什么**：
  - henchmen 这类运行的项目目录（例如 sandbox）单独设 `autoCompactWindow=150000`。
  - 空闲压缩（`CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS`，第 16 项里已经准备好但还没应用）在 Max 期间也打开。
  - 运行规范写明：等 room 消息超过 1 小时的会话，先 compact 或结束。
  - 第一步先**真机确认**已设的 300k 上限对这类会话生效。
- **估计节省**：
  - 只算"已设的 300k → 150k"这一步：模拟主会话再省 4–9 个百分点（−45% → −48~−54%）。按一次约 160M 的运行算，**约 10–15M/次**。
  - 加上冷缓存重写：3 天里 26M，几乎全部来自空闲超 1 小时后的整段重写。上下文压到 150k 后，每次重写从约 500k 降到 ≤150k，按 70% 可避免算约 18M/次。
  - **合计约 25–35M/次运行**。每周 1 次就是约 25–35M/周；不跑就是 0。
  - 还有更大的一块：如果 300k 上限其实**没有**对 henchmen 生效，那一次运行能省约 45%，即约 125M/次。
- **风险**：压缩后 agent 丢掉细节、重做工作（模拟里"每次压缩重读 30k"已经算进去，上限压到 120k 以下会开始变贵）；通宵任务的质量可能下降。
- **难度**：低（设置）到中（运行规范）。
- **怎么验证**：下次通宵后看 transcript：每个会话的最大上下文、compact_boundary 次数、距上次请求超过 60 分钟的请求有多少写入；和 11-04 的每次请求成本 45k 对比。

### 3. 去掉 `Artifact` 工具定义（设置；子 agent 优先）
- **做什么**：试 `permissions.deny: ["Artifact"]`（或其它能把工具从定义里拿掉的办法），让主会话和子 agent 不再每次都带 38.2k 字符的工具说明。需要发布网页时再临时打开。**先核实**：deny 是否真的把这个工具从发给模型的 tools 里移除。验证办法是开一个测试会话，看 transcript 里 `api-request-shape` 的 tools 是不是少了 Artifact。如果只是拦截调用、不移除定义，这条无效。
- **估计节省**：约 9.6–12.2k token × 所有请求 → 启用后 **6.7–8.5%**（子 agent 5.5、主会话 3.0），**约 13–17M/周**。通宵运行另外省约 3–4%，约 5M/次。
- **风险**：要用 Artifact 时得手动打开（历史上只用过 5 次）；改设置后第一次请求会重写一次缓存（一次性）。
- **难度**：低（但要先核实）。
- **怎么验证**：看 `api-request-shape` 的工具字符数，以及 weekly_compare 的"第一次请求上下文"：主会话应从约 42k 降到约 31k，子 agent 从约 31k 降到约 20k。

### 4. 减小 skill 列表（设置/插件）
- **做什么**：把用不上的 `anthropic-skills:*` 条目（docx/pptx/xlsx/pdf/google-workspace/morning/import-memory/computer-use/浏览器两项/skill-creator/deep-research 等，约 10k 字符）关掉，或者让它们不进列表。具体用插件开关还是某个设置项，**需要用 claude-code-guide 核实**是否可行。要保留 handoff、model-router、quant-backtest-guide、henchmen 等用户自己的 skill。
- **估计节省**：约 2.5–4.3k token/会话（含子 agent）→ 启用后 **2.5–3.5%**，**约 5–7M/周**；每次通宵运行再省约 1.5%。
- **风险**：用户偶尔要 PDF/Excel 时得重新打开；关的是官方插件，升级后可能被恢复。
- **难度**：低到中，取决于有没有现成开关。
- **怎么验证**：transcript 里 `skill_listing` 附件的字符数从 18.5k 降到 8–9k，第一次请求的上下文相应下降。

### 5. 子 agent 读文件纪律：先定位再读，禁止整文件 `cat`/大段 `sed -n`（skill 规则）
- **做什么**：在 model-router 给子 agent 的 brief 模板里加一句："读超过 200 行的文件，先 `grep -n` 定位，再读需要的 ≤80 行；不要 `cat` 多个文件拼在一起；WebFetch 时说明只要哪一节。"
- **估计节省**：启用后 ≥5k token 的单条结果占 12.8%（Bash 6.6、Read 4.6、WebFetch 1.6）。如果这些结果平均缩小一半，同时因为多一次 grep 定位抵掉约一半节省，**净省约 3%**，**约 5–7M/周**。不确定性大：有些通读任务本来就要整文件读。
- **风险**：分段读会漏掉上下文，导致误判；请求次数变多。
- **难度**：低（改规则）。
- **怎么验证**：之后统计子 agent 里 `cat`/`sed -n`/Read 整文件的平均结果大小和每个子 agent 的成本（可以复用 r5b.py 的工具细类表）。

### 6. 降低思考量：通读/调研类子 agent 用 low effort（设置/派发参数，待试验）
- **数据**：启用后 output 占 26%。可见字符（文字 + 工具参数）只能解释约 40–50% 的 output token，其余推测是思考（transcript 里思考内容是加密的，**只能间接推测**）。也就是说思考约占成本的 13–16%。主会话·Opus 实测：high effort 每次 output 平均 782，medium 658；子 agent·Opus：high 1373，medium 1365。现在大多数请求已经是 medium。
- **估计节省**：如果通读/调研类（占 25%）改成 low、思考减半，约 **2–4%**，约 4–8M/周。**非常不确定**。
- **风险**：质量下降。**难度**：中（要知道怎么按 agent 指定 effort）。**怎么验证**：A/B 同一类任务的 output token 和结论质量。

### 7. 小项（每项 ≤1%，可顺手做）
- **去掉主会话从来没用过的 SendFeedback / ScheduleWakeup / ReportFindings 定义**：约 4k token，约 1.0%（约 2M/周）。同样要先核实 deny 是否移除定义。
- **不要用 fork/续用的方式收尾**：5 次 90–144k 开局多花约 0.5–0.8M/天（2–3%）。父上下文超过 60k 时开新 agent，并给短 brief。第 16 项已经有类似规则，可以再强调。
- **session_resume 注入从约 9.5k 字符压到约 5k**：约 0.4%。
- **AGENTS.md 精简一半**：约 0.35%。
- **不建议**：
  - 主会话改用 5 分钟缓存：能省主会话写入的约 37%，即约 3%，但用户思考超过 5 分钟就要整段重写，大概率得不偿失。
  - 压 Bash 输出上限：12k 字符只省 1.2%。
  - 管重复 Read：0.16%。
  - 再压普通会话的上下文上限：0–8%，算上重读可能变贵。
