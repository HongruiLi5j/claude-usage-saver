# 第 5 轮 D：工具结果大小 / Bash 读文件的重复（2026-11-06）

报告里只有计数、读法（cat/sed 等）、扩展名和成本占比，没有抄对话正文和命令原文。带命令原文的明细只写在 `state/round5_D/`（state/ 已 gitignore）。

## 0. 结论

1. **重复读同一个没改过的文件，几乎不存在。**
   - 11-04 以来 Bash 读文件 1,439 次（两个窗口都已[实测]，下同）。其中「同一 agent、同一文件、同一段、中间没改过、也没压缩」的完全重复只有 14 次。按成本估算占 **0.02%**；启用后的窗口是 6 次，占 0.01%。
   - 全部历史（572 个 transcript、4,358 次 Bash 读）里，read_guard 回放一共只会拦 **5–10 次**，省下约 2k 单位，约等于 **0%**。
   - 同一文件确实常被读好几次：3 天里第 2 次及以后的读有 671 次，占成本 2.3%。但这些几乎都不是重复，分三类：翻页读新的一段（167）、换了过滤写法（123）、文件中途改过（101）。和之前读过的段真正重叠的部分只占 **0.04%**。
2. **Bash 读文件贵，是因为单条大、在上下文里留得久，不是因为重复。**
   - 启用后窗口里 Bash 读文件占成本 9.9%，Read 工具占 6.9%。
   - 其中 85% 在子 agent 里（8.4 / 9.9）。
   - 按单条大小看，2–5k 和 5–10k 两档合计占 7.1%。
3. **拦大文件整读（deny，提示先 grep -n）算下来不赚钱。**
   - 被拦之后要多发 1–2 次请求，每次都要把整段上下文按 cache_read 重读一遍：100k 上下文时一次约 10k 单位。这和省下来的差不多大。
   - 模拟结果：启用后窗口净省 **−0.6% 到 +0.25%**，方向都不确定；3 天窗口 0% 到 +0.5%。
   - 所以默认关闭，只留作开关。
   - 这说明候选 #5（读文件纪律，估计省约 3%）高估了。原因是没有算进多出来的请求的成本。
4. **按「只做重复拦截」做了 `hooks/read_guard.py`，没有安装。**
   - 只会输出 deny，**从不改写命令**。证据：21,125 条历史命令里 updatedInput 出现 0 次；被判成可拦的 1,536 条命令，用另一套写法复查后分歧 0 条，`bash -n` 语法检查全部通过；和 test_filter 重叠 0 条。
   - 真机 `claude -p` 实测了主会话和子 agent 两种情况，都能正确拦下并放行重试。
   - 测试 **47/47** 通过。
   - **建议：不为省额度而装**，因为预期节省约等于 0；它只是一张没坏处的安全网，每次 Bash/Read 调用多约 21ms。

## 1. 口径

- **数据**：
  - 窗口一「3 天」：11-04 00:00 PST 起有写入的 94 个 transcript，含子 agent，排除 `-private-tmp-`（基准测试）和 .secret/sealed/test2/relay-room。
  - 窗口二「启用后」：11-06 07:58 UTC 起，约 19 小时。到现在共 52.9M 单位，比 round5_where_tokens_go 写的时候多了一截。
  - 另外跑了一遍「全部历史」：572 个 transcript，668M 单位。
- **成本**：和 round5_where_tokens_go 的口径一样。
  - 一条结果的成本 ≈ tok×w + 0.1×tok×N_after。w 是它进入上下文那次请求的缓存写入单价（1.25 或 2）。N_after 是之后、压缩或会话结束前的请求数。
  - token 换算：ASCII 字符×0.43 + 非 ASCII 字符×1.39，误差约 ±20%。
  - 这些都是**估算**。请求的 usage、条数、次数是**实测**。
- **「读文件」的识别**用的是 read_guard 自己的解析器，统计和 hook 用的是同一套代码：
  - 认的命令：cat、nl、less/more、`head`/`tail`（行数、+N、-c）、`sed -n` 的行段（'a,bp'、'Np'、'a,$p'）、`python -c` 里的 `open('x').read()`，以及它们后面接的管道过滤。
  - 混在别的命令里的读也计入，标成「混合」。
  - 有 heredoc、`$(...)` 或反引号的命令看不懂，不计入。这类有 1,663 条，多数是 `python3 - <<EOF` 脚本和 `cat > f <<EOF` 写文件，不算读。
- **怎么算「文件没改过」**（历史上没法 stat 当时的文件，只能用事件推）：
  - **clean**：两次读之间没有任何可能写文件的 Bash 命令。
  - **likely**：中间有写命令，但都没提到这个文件名。
  - **possible**：中间有命令提到了这个文件名（例如 `python3 x.py`），但没有明确写它。
  - 真装上后，hook 比较的是文件内容的 sha1，不用这种推断。

## 3. read_guard 的设计（`hooks/read_guard.py`，新建，未安装）

**选的做法**：只拦「同一个 agent 重复读一个没改过的文件」，做法是 deny 加一条提示。不改写命令，也不靠 additionalContext 提醒（那只是提醒，这一次的读照样发生，省不了任何东西）。大文件整读的拦截做成开关，默认关闭。理由见 §4 的数字。

**判定重复要同时满足 6 条**，任何一条拿不准就放行：
1. **同一个 agent**：键是 `session_id` 加 `agent_id`，主会话的 agent_id 为空。子 agent 看不到父会话的输出，所以互相不共享记录。
2. **内容没变**：文件指纹相同，包括大小、mtime、inode 和**内容 sha1**。大于 2MB 的文件不参与。
3. **上次那份完整地在上下文里**：
   - 按 `tool_use_id` 在 transcript 里找到上次的 tool_result，它不能是错误，不能是落盘预览，长度要小于 30,000 字符，也不能是 "File unchanged" 那种桩。
   - 从上次到现在，transcript 里没有 `compact_boundary`。逐行解析确认，正文里提到这个词不算。
   - 子 agent 的 transcript 路径由 `<项目>/<session_id>/subagents/agent-<agent_id>.jsonl` 推出来。
4. **覆盖关系**：
   - 完全相同的读法算重复。
   - 「上次整读、这次只读其中一段」只有在上次**带行号**时才算，比如 `cat -n`、`nl` 或 Read 工具。否则模型没法照着行号在旧输出里找到那一段，典型场景是先 cat 整个文件、后来照着报错行号 `sed -n '120,160p'`。
   - 要行号的读（`cat -n`）不算被不带行号的读覆盖。
   - 管道过滤只在命令完全相同时才算。
5. **这次要读的内容 ≤ 28,000 字节。**
6. **整条命令是「纯读取」**：只由 cd、echo/printf、读文件、只往 stdout 输出的过滤组成。不能有写文件的重定向（只允许 `2>/dev/null` 和 `2>&1`）、tee、`sed -i`、sed 的 w/e/r 命令、`sort -o`、awk 的 `>`/system、`$` 展开、通配符、子 shell、后台 `&`。所以就算拦了，也不会少做任何有副作用的事。

**放行阀**：
- 被拦后原样再发同一条命令，一律放行（deny-once）。
- 命令里带 `USAGE_SAVER_RAW=1` 放行。
- **Read 工具永远不拦**，只记录。Read→Read 的重复 Claude Code 自己会处理：2.1.318 内置 "File unchanged since last read" 短桩，历史里出现过 18 次。Bash 读过之后再 Read，可能是为了 Edit（Edit 要求先 Read 过），拦了会坏事。

**fail-open**：下面任何一种情况都不输出、退出码 0：异常、看不懂的命令、坏输入、拿不到 transcript、状态文件坏了、状态目录不可写、锁 0.3 秒拿不到。

**开关**：
- `config.json` 里写 `"read_guard": {"dup": "deny"|"advise"|"off", "big": "off"|"advise"|"deny", "big_bytes": 40000}`。
- 或者设环境变量 `READ_GUARD=off`。

**开销**（实测）：每次调用约 21ms，中位数。和 test_filter 并行跑。

## 4. 回放：会触发多少、能省多少、误伤多少

在真实 transcript 的命令序列上，按原来的顺序调用 hook 的 `decide()`，和 hook 进程里走的是同一个函数。文件「有没有变」用 §1 的三种口径模拟。

| 窗口 | 会被拦的次数（clean / likely / possible） | 拦下的 token | 估计净省 | 被拦后都重试的最坏情况 |
|---|---|---|---|---|
| 3 天 | 0 / 1 / 1 | 478 | ≈1.4k 单位，**0.000%** | 多花 0.007% |
| 启用后 | 0 / 0 / 0 | 0 | 0 | 0 |
| 全部历史 | 5 / 9 / 10 | 0.8k–1.4k | ≈2k 单位，**0.000%** | 多花 0.014–0.032% |

**误伤**：全部历史里那 10 次，有 7 次是反复 `tail`/`cat` 后台任务的输出文件或日志，在等它更新。这类文件其实一直在被后台进程写，回放用的口径看不到这种写入。真装上后 hook 比较 sha1，内容变了就会放行，所以它们**不会被拦**。就算文件确实没变，拦下来告诉模型「没变」也正好是它想知道的。剩下 3 次是真重复（同一个 .md 读完 1 次或 19 次工具调用后又读），没有发现误伤的例子。

真机实测里还看到一种情况：用户明确要求「再读一次」时，模型会原样重发，这时多花一次往返，约 0.1×上下文。

**大文件整读规则**（默认关闭）的模拟：
- 候选条件：纯读或只读命令，含整读，结果 ≥ T token，结果正常。
- 拦下后：模型改用 grep -n 加 sed 读一段，取回原来大小的 f（20% 或 40%），并且多出 2 次请求，每次 0.1×上下文 + 600。
- 也可能模型坚持整读：以概率 q 原样重发，这时只多 1 次往返。

| 窗口 | 阈值 | 候选 | 这些读本身的成本 | f=0.2, q=0 | f=0.2, q=0.3 | f=0.4, q=0.3 | f=0.4, q=0.5 |
|---|---|---|---|---|---|---|---|
| 3 天 | ≥3k tok | 68 | 1.28% | +0.52% | +0.28% | +0.10% | 0.00% |
| 3 天 | ≥5k | 35 | 0.60% | +0.23% | +0.13% | +0.04% | −0.01% |
| 启用后 | ≥3k | 46 | 2.19% | +0.11% | −0.17% | −0.48% | −0.58% |
| 启用后 | ≥5k | 29 | 1.62% | +0.25% | +0.02% | −0.21% | −0.30% |
| 启用后 | ≥8k | 14 | 0.92% | +0.20% | +0.06% | −0.07% | −0.13% |

**为什么不赚钱**：hook 拦下的时候，并不知道这条结果之后还会被读多少次。在子 agent 里 N_after 中位数只有 19，而拦一次要多 1–2 次请求，每次约 0.1×100k = 10k 单位。读 5k token、之后被读 19 次，总成本约 5k×(1.25+1.9) ≈ 16k，和多出来的往返差不多。只有 11-04 那种通宵长会话（N_after 约 200）才明显划算，但那时上下文也到了 300–500k，每次往返更贵。

**所以默认关闭。**

## 5. 「不会把合法命令改坏」的证据

1. **结构上**：hook 只会输出 `permissionDecision: deny` 或 `additionalContext`，代码里没有 updatedInput。允许的命令按字节原样执行。
2. **全部历史回放**（`tools/round5/D_replay.py`，照 replay_test_filter 的做法，**不执行任何历史命令**）：

| 项 | 结果 |
|---|---|
| 历史 Bash 命令 | 24,157 次调用 / 21,125 条不同命令（1,008 个 transcript） |
| 送进 `handle()` 后输出 updatedInput / 抛异常 | **0 / 0** |
| 被判成「纯读取」（可以被拦）的命令 | 1,536 条（1,759 次调用） |
| 这 1,536 条用另一套写法复查（shlex 分词 + 白名单 + 写文件参数检查），结论不一致的 | **0**（第一版有 13 条，都是复查脚本自己误报，比如 `grep -i`、文件名里的 system；顺手把 hook 的 sed 过滤收紧了） |
| 这 1,536 条 `bash -n` 语法检查不过的 | **0** |
| test_filter 会改写的命令里被判成纯读取的 | **0** |
| 真子进程抽样 2,000 条：stdout 只能为空或合法 deny | 2,000 条全空（退出码全 0） |

3. **真机端到端**（`claude -p --setting-sources project --settings <临时>`，在 scratchpad 临时项目里用 haiku 跑；真实 settings 没参与，花了 $0.01）：
   - 主会话：第 1 次 `cat notes.txt` 正常执行；第 2 次被拦，模型看到了 read_guard 的说明；模型原样重发后放行。之后的 `pytest` 由 test_filter 正常改写、输出正常。也就是说两个 hook 同时装能共存。
   - 子 agent：hook 输入里有 `agent_id`/`agent_type`，`transcript_path` 是父会话的那个。按推出来的子 agent transcript 路径能找到结果。父会话读过的文件，子 agent 第一次读**不会**被拦；子 agent 自己第二次读才被拦。
   - 已验证：上一条 tool_result 在下一次 PreToolUse 之前就已经写进 transcript，所以「在 transcript 里找上次结果」这条路可行。
4. **测试**：`python3 tools/round5/D_tests.py` 共 **47/47** 通过。覆盖：识别，覆盖关系，重复判定的 20 种边界，fail-open 的 6 种，随机拼的 3,000 条命令从不 updatedInput 且只拦纯读取，和 test_filter 共存，性能，安装脚本 6 种。全程只用临时目录。可以用 `D_TEST_TMP=<目录>` 指定临时目录。

**和 test_filter 一起装时怎么共存**：
- 两者是两个独立的 PreToolUse 组：test_filter 的 matcher 是 Bash，read_guard 的是 Bash|Read。Claude Code 会并行调用它们。
- read_guard 从不输出 updatedInput，所以不会和 test_filter 的改写冲突。
- 它们管的命令也不相交：test_filter 只包装 pytest/npm test，read_guard 只拦纯读取，回放里重叠 0 条。
- 万一同一条命令两边都有输出，deny 优先，结果是不执行。这种情况不会出现，因为测试命令不是纯读取。

**建议**：跨工具也不值得移植 read_guard，因为上面已经算过节省约等于 0。

能跨工具通用的，是「读文件纪律」的文字规则，放进 AGENTS.md 或 GEMINI.md。但按 §4 的算法，它的净效果也可能是负的（多出来的请求要重读上下文）。所以如果写，只建议写一句：「已经读过、没改过的文件不要再读」，不要强制「先 grep 再 sed」。

## 8. 对第 5 轮候选清单的修正

- **#5「子 agent 读文件纪律」原来估计省 5–7M/周（约 3%）**：
  - 这次实测，大块的整读（≥5k）在启用后只占 2.0%（3 天 0.8%）。
  - 算上多出来的请求，模拟净省在 **−0.6% 到 +0.25%** 之间，方向都不确定。
  - 建议**降级**，不再作为优化项推进。
  - 如果还想试，先用 F2 的受控基准实测：同一批任务，加不加这条规则，比较总成本。
- **另一条线索**（已实测）：读文件的成本 85% 在子 agent 里，而且子 agent 平均单条读 2.7k，是主会话的 2 倍。那么能真正省钱的方向：
  - 减少「通读类」子 agent 本身，比如改派给 Codex（候选 #1，C 在做）；
  - 或者让子 agent 早点交回（缩短 N_after）。
  - 管住「重复读」省不了钱。
