# Round 4：子 agent·Sonnet 每次请求成本 +92% 的原因调查

> 只读调查，2026-11-06。数据取自 `~/.claude/projects/**/*.jsonl`，排除 `-private-tmp-*`，按 `message.id` 去重。成本口径与 `tools/weekly_compare.py` 相同：cache read 0.1，cache write 5 分钟 1.25 / 1 小时 2.0，input 1，output 5。改动前窗口是 10-21 到 11-06 07:58 UTC，启用后窗口是 07:58 UTC 之后。
> 脚本：`/private/tmp/claude-501/-Users-lihongrui/4a2cd3a3-02c5-4ace-9377-97e569387263/scratchpad/sub_cost.py`（提取数据）、`an.py`（逐个 agent）、`an2.py`（拆解和分桶）、`an3.py`（看最重的 agent）。
> 我的统计跑得比 weekly 晚，所以 sub·opus 多算进了本轮几个新 agent（129 次请求，weekly 里是 112 次）。sub·sonnet 两个窗口的数字和 weekly 完全一致：160 次、13.5k，以及 218 次、25.8k。

## 结论

**成本上涨来自今天的任务本身更重，不是套件造成的。把握程度：高，约 80–85%。**

剩下的不确定性在于：启用前后没有"同一种任务"可以直接对比。启用前的 16 个 Sonnet 子 agent 全是 11-03、11-04 的 relay、henchmen 试跑 agent（alpha/beta/gamma、worker、reviewer），任务极小。启用后的 11 个是"给 Codex 写项目文档"（7 个 Doc:）和调研、审核类 agent。两组任务的类型完全不同。

## 证据

### 1. 子 agent 的起始 prompt 没有变长（直接否定"套件把 prompt 撑长"的假设）

| 指标（Sonnet 子 agent） | 启用前 | 启用后 |
|---|---|---|
| agent 数 / 请求数 | 16 / 160 | 11 / 218 |
| **第一次请求的上下文**（系统提示 + 工具定义 + skill 列表 + 首条 prompt）平均 | **29.7k** | **29.7k** |
| 首条 prompt 字符数（中位数） | 1448 | 1576 |
| 每个 agent 的请求数 | 10.0 | **19.8** |
| 每个 agent 读进的工具结果字符数（中位数） | 19k | **110k** |
| 平均上下文 / 中位上下文 | 42k / 41k | **119k / 101k** |
| 每次请求的输出 token | 516 | **1228** |

model-router、handoff、quant-backtest-guide 三个 skill 只以一行描述出现在子 agent 的 skill 列表里，占不到 1k token，第一次请求的上下文完全没涨。session_resume 只在 `SessionStart:clear` 和 `SessionEnd` 时触发，context_guard 只在 `UserPromptSubmit` 时触发，子 agent 都碰不到。test_filter 只会**缩短**测试命令的输出。

### 2. 每次请求成本的拆解：涨幅主要来自"上下文越拖越长"和"输出更多"

| 每次请求成本构成（k 单位） | 启用前 | 启用后 | 差值 |
|---|---|---|---|
| cache read（0.1×） | 3.6 | 11.3 | **+7.7** |
| cache write | 7.3 | 8.4 | +1.1 |
| output（5×） | 2.6 | 6.1 | **+3.5** |
| 合计 | 13.5 | 25.8 | +12.3 |

- 约 63% 的涨幅（+7.7k）是 cache read。每次请求都要把整段历史重读一遍，而 agent 读进的文件越多、跑的轮数越多，上下文就越长。启用后每个 agent 的平均上下文是启用前的 2.8 倍，所以这部分跟着涨。
- 约 28%（+3.5k）是输出。Doc 类 agent 的要求是"先写骨架，再逐章追加"，调研类 agent 要写长篇结论，输出量是试跑 agent 的 2.4 倍。
- cache write 每次请求只多了 1.1k，说明没有出现缓存失效、反复重写缓存的问题。全部缓存写入都是 5 分钟档，没有 1 小时档。

### 3. 把上下文长度控制住以后，成本基本持平

| 上下文区间 | 启用前每次成本（请求数） | 启用后每次成本（请求数） |
|---|---|---|
| 0–40k | 11.8k (79) | 24.1k (21) |
| 40–60k | 13.9k (72) | 16.3k (30) |
| 60–100k | 24.5k (9) | 22.8k (57) |
| 100–150k | — | 27.0k (44) |
| 150k 以上 | — | 32.5k (66) |

- 上下文相近时（40–100k），前后成本差不多。启用后有 110 次请求（50%）落在 100k 以上，启用前一次都没有。
- 0–40k 区间启用后偏高，只有 21 次请求，都是 agent 的头几轮。这几轮要一次性把首批大文件写进缓存，并开始输出骨架，同样是任务形态造成的。
- 把启用后的请求按启用前的上下文分布重新加权，每次成本是 20.5k。剩下高出的部分就是上面说的输出量和头几轮写缓存。

### 4. 逐个 agent 看：贵的都是"整个代码库通读"类任务

| agent（Sonnet，启用后） | 请求数 | 最大上下文 | 总成本 |
|---|---|---|---|
| Doc: core src and engines | 63 | 276k | 1754k |
| Doc: website dashboard publish | 37 | 215k | 942k |
| Doc: glossary decisions overnight（这个是 Opus） | 22 | 229k | 766k |
| Doc: regime-statarb and ai_layer | 27 | 174k | 686k |
| Doc: scripts tests pipeline | 20 | 123k | 422k |
| Doc: handoff protocol | 14 | 110k | 357k |
| Doc: relay-room and lean-axler | 9 | 89k | 228k |

- "Doc: core src" 一个 agent 跑了 70 次工具调用，读进 35 万字符。单次最大的工具结果都来自 `cat -n src/registry.py`、`cat -n daily.py`、`cat -n src/portfolio.py src/backtest.py ...` 这类整文件 cat，每次 1.3 万到 2 万字符。
- 它的 prompt 本身就要求"读源码核实，每条断言标 文件:行号"，所以通读整个代码库是任务设计决定的，不是套件加的。
- 非 Doc 的 Sonnet agent（48 次请求，包括写 skill、D 调研、C 审核、交叉审核、Round 3 调研）每次也是 25.8k，原因是 WebFetch 拉回整页网页、输出长篇报告（每次 1449 token）。这同样是任务类型决定的。

### 5. 子 agent·Opus +10% 和主会话·Opus -53%

- **子 agent·Opus +10%**：启用前只有 3 个 agent。其中一个是 fork，起步就继承了 257k 上下文，样本太小，没有参考意义。启用后起始上下文是 30k，比启用前低，涨幅同样来自 cache write 和输出（审核、写报告）。
- **主会话·Opus -53%**：一部分是套件的真实效果（交接、守卫让主会话的上下文从 211k 降到 111k）。另一部分是"通读代码库"的重活被分给了子 agent，成本从主会话搬到了子 agent 那一栏。**所以只看子 agent 单独涨了多少会误判，要看总成本。**启用后全局每次请求成本是 -31%。

## 可落地的改法（按预期收益排序）

### 改法 1：读得多的子 agent 要分批，并且不整文件 cat（写进 model-router 的"开与关"一节）

建议加入的规则：
> 预计要读入超过约 10 万字符，或超过约 25 轮的子 agent，按目录或模块拆成多个，每个的上下文控制在约 100k 以内。prompt 里写明：先用 `grep -n` 或 `rg` 定位，再用 `sed -n a,bp` 只读相关段落，不要 `cat` 整个文件；`ls` 和 `wc` 输出加 `| head`；每写完一章就把已读的细节写进文件，不要留在上下文里反复引用。

估算影响：
- 以 "Doc: core src" 为例（63 次请求，平均上下文 181k，cache read 占 63%）。拆成 3 个 agent 后，平均上下文约 80k，cache read 每次约少 10k，共省约 630k。多出两次约 30k 的冷启动写缓存，约花 75k。净省约 550k，占这个 agent 的 30% 左右。
- 对这批 Doc 任务整体（约 4.3M），估计省 15–25%。
- 不整文件 cat 还能再减少读入量。量级不确定，粗估再省 10–20%。
- 对质量的影响很小：每份文档本来就是按模块写的。

### 改法 2：通读、摘录类的子任务按 model-router 自己的表交给 haiku

model-router 的分派表已经写了"批量读取 → haiku"，但今天的 Doc agent 是用 Sonnet 一个 agent 从读文件一路做到写文档。

建议加一条：
> 文档、盘点类任务分两步：haiku Explore agent 先按模块产出"文件:行号 + 一句话作用"的摘录（不写结论）；再由 Sonnet 或 Opus 只读摘录来写文档、判断风险。

估算影响：
- 按 API 标价，Haiku 约为 Sonnet 的 1/3（具体价格以 claude-api 文档为准；订阅额度是否同比例下降未知）。
- 如果读取阶段占这类任务成本的约 60%，整体约省 30–40%。
- 风险：haiku 的摘录可能漏掉细节。所有者要求质量优先，所以先在一个 Doc 任务上做 A/B 再推广。这一条的把握程度是中等。

### 改法 3：weekly_compare 增加"任务结构"列，避免再把任务构成的变化误判成套件的问题

不直接省钱，但能防止误判。

建议在子 agent 那一节加上：每个 agent 的请求数、第一次请求的上下文、平均上下文、cache read / cache write / 输出三项各占多少，以及"主会话 + 子 agent 合计"每天的成本。
- 套件真正需要盯的指标是"第一次请求的上下文"，今天是 29.7k，与启用前一致。这个数涨了才说明套件让子 agent 的 prompt 变长了。
- 估算影响：成本为 0，只改报告。本轮的 +92% 用这几列一眼就能看出是任务变重。

## 局限

- 启用后只有约 2.5 小时的数据，Sonnet 子 agent 只有 11 个，其中 7 个来自同一批 Doc 任务，结论受这批任务主导。
- 启用前后没有同类任务可以直接对比。要彻底排除套件的影响，可以等哪天在套件下跑一次和 11-03 一样的 relay 试跑 agent，看每次成本是否仍在 13k 左右。
- 成本是按 API 价格比折算的，不等于订阅额度的百分比。
