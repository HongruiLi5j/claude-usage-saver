### 1.2 "每次请求"这个口径本身有问题【判断】

每次请求成本 = 总成本 / 请求数。这个分母是**套件和工作方式都能改变的量**，所以它不是一个稳定的"单位"。

1. **成本几乎就是上下文长度的线性函数。** 实测回归：改动前 `cost_k = 10.4 + 0.103 × ctx_k`，启用后 `cost_k = 10.0 + 0.115 × ctx_k`。按上下文分桶后，两期的每次请求成本几乎一样：

   | 上下文 | 改动前 | 启用后 |
   |---|---|---|
   | <50k | 17.0k | 17.9k |
   | 50–100k | 18.2k | 17.7k |
   | 100–150k | 22.9k | 22.6k |
   | 150–200k | 28.4k | 32.9k |
   | 200–300k | 33.0k | 36.4k |
   | ≥300k | 62.7k | （无） |

   把改动前（去掉 AQ）的成本按**启用后的上下文分布**重新加权，得到 21.6k，和启用后的 21.5k 一样。**所以 -33% 全部来自"请求时上下文更短"，没有任何"同样长的上下文变便宜"的成分。**

2. **把工作拆成多个子 agent，每次请求的成本会机械性地下降，但总量不一定下降。** 每个子 agent 从约 30k 的上下文开局，请求自然便宜。但每个子 agent 都要重新付一遍约 30k 的启动税，还会重复读同样的文件。最终的结果可能是请求变多、单次变便宜、总量反而更高。每次请求成本对这种情况是**看不见的**。
3. **固定开销实际上涨了，被平均数掩盖了。** 主会话第一次请求的上下文中位数，从改动前的 25.5k 涨到启用后的 48.5k【实测】。原因包括 session_resume 注入、AGENTS.md、更多 skill 和 agent 列表等，不全是套件造成的。这是一个真实存在的成本**上升**。
4. **跨模型直接相加。** 这个单位里 Opus 和 Sonnet 的 token 按同样的价格算，而启用后 Opus 的请求占比是 75%（之前 45%）。本项目自己的 exercism 基准里，两个模型 token 数几乎相同，费用比是 0.498（round2_review_BD.md），也就是 Opus 约为 Sonnet 的 2 倍。按这个比例加权以后【实测数据 + 价格比假设】：

   | | 不加权 | Opus 按 2 倍 Sonnet 加权 |
   |---|---|---|
   | 改动前（全部） | 32.2k | 51.2k |
   | 改动前（去掉 AQ-*） | 27.7k | 36.8k |
   | 启用后 | 21.5k | **37.2k（与去掉 AQ 的基线相比 +1%）** |

   订阅额度对 Opus 和 Sonnet 怎么折算，**不知道**。所以至少要把两种口径都报出来。

### 1.4 样本量与不确定性【实测】

- **分析单位应该是会话或天，不是请求。** 同一个会话里的请求高度相关：上下文是累积的，任务是同一个。把 1,623 次请求当作独立样本，标准误会严重低估。
- 会话级 cluster bootstrap（4,000 次重抽，比的是总量比）：

  | | 每次请求成本 | 95% CI |
  |---|---|---|
  | 改动前（全部，497 个会话） | 32.2k | [28.2, 35.6] |
  | 改动前（去掉 AQ，409 个会话） | 27.7k | [23.1, 31.1] |
  | 启用后（61 个会话） | 21.5k | [19.7, 23.4] |
  | 变化：相对全部基线 | -33% | **[-41%, -20%]** |
  | 变化：相对去掉 AQ 的基线 | -21% | **[-33%, -5%]** |

  这些 CI **只反映会话之间的抽样误差**，没有包含"任务组合不同"带来的偏差，而后者大得多。
- **按天看**：改动前 17 天的日均每次请求成本是 29.3k，标准差 6.9k，范围 20.3–45.4k。下一天的 95% 预测区间约为 [14k, 44k]。启用后的 21.5k 在区间内，而且改动前有 3 天（10-29、11-01、11-02）本来就 ≤22k。

### 1.5 选择偏差与回归均值【判断】

- **套件是在一次极端事件之后启动的。** 11-04 是整个基线里最贵的一天（日成本 281.8M，是中位数的 24 倍；每次请求 45.4k，是最高的一天），套件正是为了应对它在 11-05/06 启用的。"在最坏的时刻之后开始干预"，下一期几乎一定会变好，这就是回归均值。基线又恰好覆盖了这个极端值。
- **启用后的窗口是自选的。** 它恰好是"做套件本身"的工作，参与者会刻意开短会话、多用子 agent、及时 /clear。这种霍桑效应混在工作方式里，没法和套件分开。
- **基线起点（10-21）的选择**也会影响结果：只用最近 7 天（去掉 AQ）是 27.0k，用全部是 32.2k。没有预先规定基线窗口，就有分析者自由度。

### 1.6 weekly_compare.py 的具体口径问题（建议 D 或主会话修，我没有改）

1. `days` 按"有记录的本地日期"计数。启用后被算成 2 天，但其中 11-05 只有 23:58 之后的 17 次请求，所以**每天成本 9.8M 被低估约一半**。应该按实际覆盖的小时数换算，或者只算完整日。
2. 没有请求的日子不计入分母（10-27、10-28 这种近乎为零的日子算了，完全没用的日子不算）。所以"每天成本"既不是日历日均值，也不是活跃日均值。
3. 平均上下文是按请求平均的，长会话的权重被放大。11-04 一天的 6,211 次请求就决定了基线的 211k。应该同时报会话级的中位数。
4. 跨模型直接相加。建议加一列按模型单价加权的成本。
5. "≥3 个完整天"这条提醒写了，但头条数字没有遵守。

## 2. 审查对象 2：round5_where_tokens_go.md

### 2.1 成本构成

- **第 1 节的总成本构成**（cache_read 75%/47% 等）是【实测】，可靠。
- **"按上下文里是什么"拆分**（固定前置 26.5%、工具结果 29.4% 等）是【估算】。字符换算成 token 的误差约 ±20%，分摊规则也是人为选的（cache_read 按 token 占比分给已有条目）。这种分摊不唯一：按"边际节省"算（去掉这一条，后面每次请求少读多少），结果和按"平均分摊"算会不一样。用来**排序**大致可以，不能当作精确份额。
- **口径不一致**：第 4 节说主会话"守卫都发出了，第一次在 162–174k"，而第 5 节的固定前置和第 6 节的子 agent 都只用了**一天**的数据。那天的任务组合是"复核和通读特别多"，报告第 7 节自己也承认了这一点。

### 2.2 "每周省 X M"的外推【实测 + 估算】

- 基数"28.3M/天 × 7 ≈ 198M/周"。改动前 16 个日历日的日成本：均值 37.8M，标准差 68.8M，中位数 11.9M，变异系数 1.82；活跃日的对数标准差是 1.22。滚动 7 日总量在 105–439M 之间。
- 从改动前的日成本分布里有放回地抽样模拟：**"1 天 × 7"和"真实 7 天之和"的比值，95% 区间是 [0.00, 12.4]，P(偏离超过 ±50%) = 0.76。** 1 天 × 7 基本没有信息量。
- 每项节省都是"份额 × 节省比例 × 周基数"三个不确定量相乘。用对数近似：

  ```
  Var(log S) ≈ Var(log share) + Var(log p_saved) + Var(log base_week)
  ```

  其中 base_week 一项，用 1 天外推时对数标准差约 1.2，用 2 周数据时约 0.5。所以无论另外两项多准，区间都至少是 ×/÷ e^{1.96×1.2} ≈ ×/÷10。
- **各项节省不能相加。** 第 1 项把子 agent 改派给 Codex，被改派的子 agent 就不再付 Artifact 工具定义（第 3 项）和 skill 列表（第 4 项）的钱。所以第 3、4 项在第 1 项实施后的节省会缩小约 33%（第 1 项的份额）。汇总表按"每周估计"排序，暗示可以叠加，应该改成"按顺序实施时的边际节省"。
- **建议改写方式**：把节省报告成**"每单位工作的相对节省"**，并用第 5 节的受控对比来测。周节省 = 相对节省 × 周基数，周基数用 ≥2 周的数据，给出预测区间。对固定前置这类确定性改动，可以直接算：

  ```
  ΔC_week ≈ Δp × (w_write × N_cache_writes_week + 0.1 × N_requests_week)
  ```

  其中 Δp 是前置减少的 token 数，用 `api-request-shape` 或第一次请求的 cache_creation 实测；w_write 是 1.25 或 2.0；N 用多周的实测分布。这样 Δp 没有统计不确定性，不确定性只来自 N。

## 3. 审查对象 3：scorecard、盲测、回放能不能当作"质量提升"的证据

先分清两种"质量"：**(Q1) 套件的 hook 功能是否正确**；**(Q2) 用了套件之后，AI 干活的质量是否下降**。省额度的优化最大的风险在 Q2，比如压缩丢失细节、改派 Codex 读错、low effort 漏判。目前**没有任何一个指标测到 Q2**。

### 3.1 scorecard 107/107【判断】

- **构造性的 100%。** 场景来自 round1/2 发现的问题和复核意见，是在 bug 修完以后、照着修好之后的预期行为写的（"当前版的 ✗ 就是还没修的问题"）。v0 34% → 100% 衡量的是"修了多少已知问题"，不是"质量提升了多少"。这本质上是为了通过测试而写测试。
- **分母在变**：v0 是 20/58，当前是 107/107，新增的 49 个场景在 v0 里"不适用"。
- 107/107 的 Wilson 95% CI 是 [96.5%, 100%]，但这个 CI 没有意义，因为场景不是从"可能出错的情况"里随机抽出来的。
- **正确用法**：当作**回归门槛**（每一轮必须保持 100%，不能退步），不当作提升指标。

### 3.2 盲测 56/60【实测 + 判断】

- **原始结果是 48/60**（80%，Wilson CI [68%, 88%]）。分诊人读过实现以后，把 10 条判为"夹具假设错误"（并把夹具改成和实现一致），1 条判为"文档不清"，1 条判为真 bug。
- **问题 1：裁决是事后做的，而且由看过实现的一方来做。** 12 条失败里有 10 条判定"实现对、测试错"。其中一部分理由确实成立（比如 MARK 的字面值），但"公开文档没写 rate.json 格式、日志目录"本身就是接口缺陷。盲测的价值正在于此：外部使用者照文档写，就会踩这些坑。
- **问题 2：修正后的结果没有全部重跑。** 29 个 TF 场景被跳过，56 里的 TF25/26 是"按代码推演"出来的。
- **问题 3：修正后暴露了 2 条原来碰巧通过的（CG11、SR06）。** 这说明原始的 48 条通过里也有假阳性，测量效度有问题。
- **问题 4：60 个场景出自同一个生成者（Codex），彼此相关，跑一次。** 不同轮的盲测题不一样，所以 round4 和 round5 的通过率**不能直接比**。
- **建议**：
  1. 头条报原始通过率，分诊后的结果作为附注。
  2. **在看结果之前**就写好裁决规则，比如"文档没写明的行为，一律按测试失败算"。
  3. 裁决人不看实现，只看公开文档。
  4. 改了夹具以后，全部场景必须重跑。
  5. 比较两个版本时，用**同一套新题**同时跑旧版和新版，做配对比较（McNemar），而不是拿这一轮的题和上一轮的题比。

### 3.3 回放 19,951 条改坏 0【实测】

- 真正被改写的只有 82 条 unique 命令（99 次），其余命令根本没被碰过。所以有效分母是 82：0/82，按三法则 95% 上界是 3/82 ≈ 3.7%。
- 只检查了 `bash -n` / `zsh -n` 的语法，没有检查语义（退出码、输出是否完整）。
- 另外，1,644 条测试命令里有 1,562 条没有被改写（漏网），这限制了 test_filter 能省的上限。这是一个关于"覆盖率"的数，应该和"0 改坏"一起报。

| 层级 | 指标 | 定义 | 用途 |

| 主（受控） | **每个成功完成任务的成本** | 同一任务集合、配对运行，`Σ quota_cost / Σ success`；同时报几何均值比 | 判定"这一轮是否更省" |

## 5. "每一轮都必须比上一轮好"的判定协议

### 5.0 原则【判断】

1. **每一轮是否变好，只能由受控对比来判定。** 观察数据里，一轮只有几个小时，同时改了好几项，任务组合每轮都不同，按 1.3 节的分析，根本识别不出效应。观察数据只用于跨周的合理性检查。
2. **必须允许"持平"作为诚实的结果。** 如果硬性要求"每轮都要更好"，又不控制假阳性，那么即使什么都没改，也大约有 2.5%（单侧）的概率会"看到改善"。另外还会诱导挑指标、挑子集。比较好的做法是：只有经过确认的改善才能记入累计数字（棘轮）。
3. **边际收益在递减，而最小可检测效应（MDE）是固定的。** 后面几轮的改进越来越小，n 不变的话就测不出来。需要提前规划加大 n，或者对确定性的改动改用机制测量（5.2.8）。

### 5.1 指标层级（预先登记，每轮不变）

- **门槛 G**（全部必须满足，否则这一轮直接判"未变好"）：
  - G1：scorecard 在冻结场景 + 新增场景上 100%。
  - G2：回放改坏 = 0，同时报告被改写的条数 k；如果 k < 50，要注明"检测力不足"。
  - G3：新盲测题上配对比较，新版不比旧版差。也就是说，旧版通过、新版失败的场景数为 0；如果有，要按**预先写好的规则**裁决。
  - G4：红线检查（没有修改真实的 settings 等）。
- **主指标 P**：受控对比中，"新版 / 上一轮"的每任务成本几何均值比 R。
- **共同主指标 Q**：任务成功率之差 Δp = p_new − p_old（非劣效）。
- **次指标 S**：总量比（Σ 成本之比）、每任务请求数、峰值上下文、前置 token、输出 token、耗时。只用于解释，不用于判定；多个次指标一起做检验时，用 Holm 校正。

### 5.2 受控对比的设计要求（给 F2）

1. **两臂只差被测的那一项。** 旧基准里，`baseline_opus` 和 `new_sonnet` 同时换了模型和配置，所以效应无法归因。每个臂用各自的 `--settings <临时文件>`，在同一个临时 HOME 副本、同一个仓库快照、同一条 prompt、同一个完整的模型 id 下运行，并记录 `version`、`effort`。
2. **配对 + 随机顺序 + 同一时段。** 每个任务的两个臂背靠背运行，臂的先后随机；任务顺序每一轮重复都重新打乱。这样可以抵消时间漂移、限流和模型侧的变化。
3. **控制缓存状态。** 旧基准 C_lookup 的成本呈两档分布（0.072 和 0.052），符合"缓存热/冷"的模式。要求：每个块开始前，每个臂各跑一次热身（丢弃不计）；记录每次运行第一次请求的 `cache_creation_input_tokens` 和 `cache_read_input_tokens`，作为协变量，或者分开报告。
4. **重复次数**：每个任务每个臂 r = 3（成本方差较大的长任务用 r = 5）。分析单位是**任务**：先在任务内对 r 次重复求平均，不能把重复当成独立样本。
5. **任务数 n 用公式确定，先跑小规模试点估计方差。** 对任务 i，`d_i = mean_r log C_new − mean_r log C_old`：

   ```
   Var(d_i) = σ_τ² + 2·σ_ε²/r        （σ_τ：效应在任务之间的异质性；σ_ε：同一任务重复运行的噪声）
   MDE(相对) = 1 − exp( −(t_{1−α/2,n−1} + t_{1−β,n−1}) · σ_d / √n )
   ```

   - 已有数据【实测】：旧基准 4 个小任务 × 5 次重复，σ_ε（log 成本的组内标准差）是 0.055–0.174，合并约 0.11。exercism 26 题配对，sd(d) = 0.071。这两组都是小任务。
   - 最小可检测效应（α = 0.05 双侧，检验力 80%）【估算】：

     | 场景 | r | σ_d | n=10 | n=20 | n=30 | n=60 |
     |---|---|---|---|---|---|---|
     | 小任务（σε=0.11，设 στ=0.05） | 3 | 0.10 | 9.7% | 6.6% | 5.3% | 3.7% |
     | 真实 agent 任务（假设 σε=0.35，στ=0.15） | 3 | 0.32 | 27.5% | 19.2% | 15.7% | 11.2% |
     | 同上 | 5 | 0.27 | 23.4% | 16.2% | 13.2% | 9.4% |
     | 长会话/多 agent（假设 σε=0.5，στ=0.2） | 3 | 0.46 | 36.4% | 25.9% | 21.4% | 15.4% |

   - 反过来，要检测 5% / 10% / 20% 的效应，所需任务数：σ_d = 0.10 时分别要 32 / 10 / 5 个；σ_d = 0.32 时要 308 / 75 / 19 个。
   - **含义**：像"去掉 Artifact 工具定义（约 7%）"这种效应，在真实任务上用端到端基准几乎测不出来。这类改动应该走第 8 条的机制测量，端到端基准只负责检查非劣效。
   - **试点**：8 个任务 × 2 臂 × 3 次，估计 σ_ε 和 σ_τ，然后用上面的公式确定 n，并**在正式运行之前写进 F2 报告**。
6. **任务集合要有代表性，而且分开开发集和确认集。** 按所有者的真实工作分层抽样：bugfix、审查/通读、查找、新功能、写文档、多 agent、长会话，每层至少 3 个任务。基线通过率要在 30–90% 之间，避免天花板效应：旧基准 142/142、26/26 全部通过，质量完全没有区分度。在开发集上调优，**最终数字只报确认集**，以免赢家诅咒。
7. **质量评分**：用隐藏的评分器（测试、固定答案、diff 约束），不能用 AI 自评。质量的非劣效检验需要的 n（配对二分类，单侧 α = 0.05，检验力 80%，`n ≈ (z_{1−α} + z_{1−β})² · p_disc / δ²`，p_disc 是不一致对的比例）：p_disc = 0.1 时，δ = 5 个百分点要 248 个任务，δ = 10 个百分点要 62 个，δ = 15 个百分点要 28 个。**30 个任务只能排除 ≥15 个百分点的质量下降**，报告里必须如实写明。
8. **确定性改动用机制测量。** 前置 token、工具定义大小这类改动，用第一次请求的 `cache_creation_input_tokens`，或者 `api-request-shape` 里 tools 的字符数直接测出 Δp。它的方差接近 0，然后用 2.2 节的公式换算成每周节省。端到端基准只负责证明"请求数、成功率没有变差"。
9. **样本量固定，不中途偷看。** n 写好以后一次跑完。如果一定要中途看（比如受预算保护），就用两阶段设计：中期分析只在 p < 0.005 时停止，最终分析用 α = 0.048（O'Brien–Fleming 的近似）。
10. **成本单位**：主口径用 `total_cost_usd`，同时报 token 单位，并记录每个臂里各模型的用量（`modelUsage`）。

**排程示例**：

```python
import random
def schedule(tasks, arms=('prev', 'new'), reps=3, seed=20261106):
    """配对 + 随机：每次重复重新打乱任务顺序；同一任务的两臂背靠背、先后随机。"""
    rnd = random.Random(seed); plan = []
    for r in range(reps):
        for t in rnd.sample(tasks, len(tasks)):
            order = list(arms); rnd.shuffle(order)
            plan += [(t, a, r) for a in order]
    return plan          # 每个块开头另加每臂一次热身（不计入），记录首请求 cache_creation/cache_read
```

**分析示例**（置信区间：几何均值比用配对 t 区间；总量比和成功率差用按任务重抽的 bootstrap；n < 20 时用 BCa 或 t 区间，不要用百分位 bootstrap）：

```python
import numpy as np, pandas as pd
from scipy import stats
def analyze(df, A='prev', B='new', nboot=10000, seed=0):
    """df 列：task, arm, rep, cost（total_cost_usd）, pass_（0/1，隐藏评分器给出）。分析单位 = 任务。"""
    g = df.groupby(['task', 'arm']).agg(lc=('cost', lambda x: np.log(x).mean()),
                                        c=('cost', 'mean'), p=('pass_', 'mean')).unstack('arm')
    d = (g['lc'][B] - g['lc'][A]).values; n = len(d)
    m, se = d.mean(), d.std(ddof=1) / np.sqrt(n); t = stats.t.ppf(0.975, n - 1)
    geo = np.exp([m, m - t * se, m + t * se])                       # 每任务等权的成本比
    rng = np.random.default_rng(seed); idx = rng.integers(0, n, (nboot, n))
    cA, cB = g['c'][A].values, g['c'][B].values
    sumr = cB[idx].sum(1) / cA[idx].sum(1)                          # 总量比（大任务权重大）
    dp = (g['p'][B] - g['p'][A]).values; DP = dp[idx].mean(1)
    return dict(n_tasks=n, geo_ratio=geo,
                sum_ratio=(cB.sum() / cA.sum(), *np.percentile(sumr, [2.5, 97.5])),
                pass_diff=(dp.mean(), *np.percentile(DP, [2.5, 97.5])))
```

### 5.3 判定规则（每轮在跑之前登记，跑完之后照着判）

第 k 轮宣称"比第 k−1 轮好"，必须**同时满足**：

1. 门槛 G1–G4 全部通过。
2. **省额度路径**：在**确认集**上，几何均值比 R 的 95% CI 上界 < 1.00，且点估计 ≤ 0.95；总量比的点估计 < 1。
   **或者质量路径**：成功率之差的 95% CI 下界 > 0，同时成本非劣效（R 的上界 < 1.05）。
3. 质量非劣效：Δp 的 95% CI 下界 > −δ。δ 事先确定，n 允许时取 10 个百分点；n 不够时，报告必须写明"只能排除 ≥X 个百分点的质量下降"。
4. 对比对象是**同一时段运行的第 k−1 轮配置**，不能和历史数字比。同时保留一个冻结的 v0 臂，用来报告累计效果。
5. 如果一轮里同时改了多项，主检验只做"整包 vs 上一包"这一次。单项归因只限于单独做过对比的项，多项一起检验时用 Holm 校正。

报告模板：

```
第 k 轮 vs 第 k−1 轮（确认集 n=__ 个任务 × r=__，同一时段 __，CC __，模型 __）
```

### 5.4 观察数据怎么调整（weekly_compare 的升级要求）

用于跨周的合理性检查，**结论只能是"与受控结果一致/不一致"**：

1. **时间窗**：启用后至少 7 个完整日，并且至少 30 个主会话；基线窗口固定、预先登记，比如"改动前连续 14 个完整日"，以后不再改。
2. **分析单位**：会话级（主会话 + 它派生的子 agent 合并为一个工作单元），按天聚类。
3. **分层 + 直接标准化**：层 = 工作类型（项目或无人值守 henchmen / 交互式）× 模型 × 是否多 agent。把启用后的各层成本按冻结的参考组合加权；如果参考组合里能被覆盖的层不到 80%，就不报这个数。

   ```python
   def standardized(after, ref, strata=('work_type', 'model', 'multi_agent')):
       """after/ref：会话级表，列含 cost、units（真人 prompt 数）和分层列。返回按 ref 组合加权的每单位成本和覆盖率。"""
       s = list(strata)
       m = after.groupby(s).apply(lambda x: x.cost.sum() / max(x.units.sum(), 1))
       w = ref.groupby(s).units.sum(); w = w / w.sum()
       common = m.index.intersection(w.index); cov = w[common].sum()
       return (m[common] * w[common]).sum() / cov, cov      # cov < 0.8 不报
   ```

4. **天级中断时间序列**（基线 ≥14 天时）：

   ```
   log(Y_d) = β0 + β1·post_d + β2·t_d + γ'X_d + ε_d
   ```

   Y_d 是每个工作单元的成本；X_d 是当天无人值守的占比、子 agent 占比、Opus 占比、平均真人 prompt 数；标准误用 Newey–West（lag = 2）。`statsmodels.OLS(...).fit(cov_type='HAC', cov_kwds={'maxlags': 2})`。效应 = exp(β1) − 1。
5. **安慰剂日期**：把"启用日"挪到基线里的每一个日期，重复上面的计算，得到零效应时的分布。真实效应要落在这个分布的 5% 尾部之外。
6. **阴性对照**：选一些套件不该影响的指标，比如交互式主会话每次请求的 output token、每个子 agent 的工具调用数。如果它们也大幅变化，说明工作组合变了，这时应该降级结论。
7. **价格加权**：同时报 token 单位和按模型单价加权的口径。
8. **把通宵运行单独作为一层**：每次 henchmen 运行的成本差异很大（11-04 一次就占了基线的 46%），不能和日常使用混在一起取平均。

### 5.5 下面这些情况，**不能**宣称变好

1. 启用后不足 7 个完整日或 30 个主会话（观察数据）；受控对比的 n 低于预先登记的值。
2. 效应的 CI 跨过 1，就只能说"未检测到差别"，不能说"没有差别"，也不能说"趋势向好"。
3. 只有"每次请求成本"下降，而每任务成本、每个工作单元的成本或总量没有下降。也就是请求变多、单次变便宜。
4. 结论对调整方式敏感：原始结果和标准化（或价格加权）结果的差，超过效应本身的一半。本轮就是这样：-33%、-21%、+1%。
5. 两臂或两期之间模型、Claude Code 版本或 effort 分布变了，而且没有在同一时段对照。
6. 质量没有测，或者两臂都 100% 通过（天花板）。这时只能写"未见质量下降（无检测力）"。
7. 测试或裁决是在看到结果之后才写或修改的，比如盲测的事后改判。
8. 只在开发集上有效，确认集上没有复现；或者是从多个指标、子集里挑出来的最好那个，又没有做校正。
9. 基准任务没有代表性（比如玩具题），这时结论只能限定在"小任务"范围内。
10. 每周节省的周基数少于 2 周的数据，或者没有给出预测区间。
11. 门槛 G1–G4 有任何一项不过。

## 额度折算

所有者把"订阅额度里 Opus 和 Sonnet 怎么折算"交给我们自己定。这一节是数据估计和最终采用的比例。

### 结论

**采用：额度成本按 API 美元计算。**

- 按 token 算，Opus 5.5 的额度成本是 Sonnet 5.5 的 **2 倍**（R = 2.0），input、缓存写入、缓存读、output 四类都一样。
- 换算关系：
  - 5 小时额度的 1% ≈ Opus 约 1.1 API 美元 / Sonnet 约 1.5 API 美元；
  - 周额度的 1% ≈ 9–10 API 美元。
- 数据和先验合并后的估计是 **R = 2.26（95% 区间 1.43–3.56）**；只看数据是 2.68（1.18–4.91）。两者都和 2.0 相容。所以采用最简单、可以从官方定价页核对的 2.0，并把 R = 2.7 作为敏感性分析的口径一起报。

### 数据从哪来【实测】

1. **额度读数没有历史。**
   - `state/rate.json` 只保留最新一条，每次刷新都覆盖。
   - `state/last_status_sample.json` 只有 11-06 00:03 的一条，当时周额度 79%、5 小时额度 2%。
   - `limit_events.jsonl` 不存在：limit_logger 只在撞到上限时写，而启用后还没撞过。
   - statusline 没有写历史。telemetry 和 stats-cache 里也没有额度百分比。
   - 所以我在 18:44–18:55 PST 每 15 秒只读轮询一次 rate.json。这是 5 小时窗口 18:20–23:20 内的一段，读数从 40% 涨到 78%，共 37 个不同读数；同一时段周额度从 5% 涨到 9%。
2. **transcript 里有 4 次"撞到 5 小时上限被拒"的记录**（`quotaLimits` / `rate_limit_info`，status=rejected），可以作为"此刻 = 100%"的锚点：

   | 窗口 | 撞顶时，窗口内的累计用量（API 美元） | 模型 |
   |---|---|---|
   | 11-03 23:30 | 约 232 | 纯 Opus |
   | 11-04 04:30 | 约 235 | 纯 Opus |
   | 10-29 18:50 | 约 20 | 主要是 Opus |
   | 10-23 11:30 | 约 20 | 纯 Fable |

   后两次的用量只有前两次的约 1/10。原因可能是 transcript 之外的用量（官方帮助中心写明 **claude.ai 网页/桌面聊天和 Claude Code 共享额度**），也可能是限额本身变过。这 4 次撞顶时窗口里都只有一种模型，所以对比例 R 没有信息，**已剔除**。
3. **同一时段的 token**：取 `~/.claude/projects` 下的全部 transcript，包括子 agent 和 `-private-tmp-` 基准会话（基准也消耗额度），按 message.id 去重，按模型分 input / cache_write_5m / cache_write_1h / cache_read / output 五列。
4. **先验**：
   - 官方定价页（platform.claude.com/docs/en/about-claude/pricing，11-06 读取）：

     | 模型 | input | 缓存写入 5m | 缓存写入 1h | 缓存读 | output |
     |---|---|---|---|---|---|
     | Opus 5.5 | $4 | $5 | $8 | $0.20 | $20 |
     | Sonnet 5.5 | $2 | $2.50 | $4 | $0.10 | $10 |

     （每百万 token。）**两个模型每一类都恰好差 2 倍，缓存读都是 input 的 0.05 倍。** 注意：claude-api skill 里缓存的 Sonnet 缓存读价格是 $0.20，和官方页不一致，以官方页为准。
   - 帮助中心（support.claude.com 文章 11049741 和 11145838，11-06 读取）：**没有给出模型之间的比例**；写明了 Claude 和 Claude Code 共享额度，Max 套餐对 Fable 有单独的周额度。旧版 Opus 4 时代的文章说"Opus 触顶约快 5 倍"，而当时的 API 价格比也是 5 倍。所以先验取 ln R ~ N(ln 2, 0.30²)。

### 模型与估计【实测数据 + 统计模型】

把每个模型的 token 换算成"本模型单位"：u = input + 1.25·写入5m + 2·写入1h + 0.05·缓存读 + 5·output。两个模型的类别结构完全相同，所以 R = a/b 就是"同样的 token，Opus 消耗的额度是 Sonnet 的几倍"。

```
Δy_k = a·ΔU_opus,k + b·ΔU_sonnet,k + h·ΔU_haiku,k + ε_k     （a, b, h ≥ 0；NNLS）
```

- y 是 5 小时额度的百分比。每个整数读数取它**第一次出现**的时刻，所以只用同一个窗口，重置时刻已经剔除。
- ε 包含整数量化误差（每个读数约 ±0.5，均匀分布，方差 1/12）和 transcript 时间戳与读数之间的滞后。

| 方法 | a | b | R = a/b |
|---|---|---|---|
| 增量 NNLS | 3.50 | 1.31 | **2.68** |
| 累计 NNLS + 截距 c（transcript 之外的用量） | 3.22 | 1.41 | 2.29（c = 0.00，说明这个窗口里没有 transcript 之外的用量） |
| 块 bootstrap（块长 3，4,000 次） | [2.74, 3.87] | [0.76, 2.38] | 中位数 2.72，**95% [1.18, 4.91]** |
| 价格先验 + 数据（对数正态共轭） | | | **2.26，95% [1.43, 3.56]** |

a、b 的单位是"额度百分比 / 百万本模型单位"；bootstrap 一行给的是 95% 区间。

敏感性分析：
- **缓存读的额度权重识别不出来。** 权重取 0 / 0.05 / 0.10 时，R = 3.31 / 2.68 / 2.13，残差平方和 3.71 / 2.57 / 2.49。0 明显更差；0.05（定价页）和 0.10 区分不开。
- **两个模型的用量是一起动的。** 整段序列里，Opus 占 API 美元的比例只在 0.79–0.86 之间变化。所以 R 的信息主要来自 18:46–18:48 那段 Sonnet 用量突增，区间偏宽。
- **周额度的数据没法用。** 上一周窗口 79% 对应 799 美元（10.1 美元/1%），本周 4% 对应 36 美元（9.1 美元/1%）。两次每 1% 的美元数一致，说明"额度 ∝ API 美元"的整体尺度是稳定的。但两次的模型组合几乎一样（Opus 都占 82–87%），区分不了 Opus 和 Sonnet。本周 5→9% 的序列拟合落在边界上（b = 0），不能用。

### 为什么用 2.0，而不是 2.26 或 2.7【判断】

- 数据的区间包含 2.0，后验也包含 2.0。在现有证据下，2.0、2.26、2.7 统计上分不开。
- 2.0 有外部依据，可以核对：官方定价页，而且历史上额度比一直跟着价格比走。它在四类 token 上都一样，可以直接用 `total_cost_usd` 或按定价页算 API 美元，不需要再维护一套自己估出来的权重。
- 用途看的是"排序和相对节省"。只有当两个优化的 Opus/Sonnet 构成差别很大时，R 的取法才会影响结论。所以报告里，凡是涉及模型切换的结论，同时报 R = 2.0 和 R = 2.7 两个口径；两个口径结论相反时，标注"取决于额度折算，不确定"。
- **附带发现**：`tools/weekly_compare.py` 里缓存读的权重是 0.1，但对 Opus 5.5 和 Sonnet 5.5 应该是 0.05（定价页）。这会让缓存读的成本被高估一倍，也会让"上下文更短"的效果被夸大。按官方 API 美元重算第 1 节：
  - 每次请求的成本：改动前（去掉 AQ）5.52 美分 → 启用后 5.79 美分（+5%）；
  - 和全部基线比：6.96 → 5.79 美分（-17%）。
  - 这和第 1.2 节"按价格加权后看不到下降"的结论一致。

### 什么时候应该重估

满足下面任何一条就重估：

1. **攒够 ≥5 个不同的 5 小时窗口的读数序列，而且其中至少 2 个窗口里 Sonnet 占 API 美元 ≥40%。** R 需要模型组合有变化才能识别出来，光有窗口数没用。这需要 statusline 把读数**追加**写到一个历史文件，比如 `state/rate_history.jsonl`，每行写 sampled_at、5h%、7d%、resets_at，按 sampled_at 去重。statusline.sh 不归 F1，建议交给它的负责人做。
2. 后验 95% 区间不再包含 2.0。
3. 模型版本或价格变了，比如出了新的 Opus 或 Sonnet，或者定价页改了。
4. **11-21 从 Max 换到 Pro 之后。** 不同套餐的折算方式可能不同，换完以后要重估。
5. 帮助中心公布了官方比例。

**想更快、更准的话，做一次受控校准**：
- 找一个没有其他会话的 5 小时窗口，在临时目录里用 `claude -p` 跑同一批任务，纯 Sonnet 一段、纯 Opus 一段，交替进行（ABAB），每段让额度涨 5–10%。
- 估计量：

  ```
  R̂ = (Δy_O / U_O) / (Δy_S / U_S)
  ```

- 每段的量化误差约 0.41%（两端各 ±0.5% 均匀分布，差值的标准差是 √(1/6)）。每段 Δy = 5%、每个模型 2 段时，sd(ln R̂) ≈ 0.12，95% 区间约 ±25%；Δy = 10% 时约 ±12%。
- 代价是约 20–40% 的一个 5 小时窗口，要所有者同意。
